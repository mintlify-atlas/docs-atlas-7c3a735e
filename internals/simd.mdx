## AVX2 fundamentals

AVX2 (Advanced Vector Extensions 2) is the SIMD instruction set that oxsv is built around. The key properties that matter for CSV processing:

- A single YMM register holds **256 bits = 32 bytes** of data.
- `VPCMPEQB` compares 32 bytes against a broadcast value simultaneously, producing a 32-bit mask where each bit corresponds to one byte.
- `VPMOVMSKB` extracts that mask into a general-purpose register.
- `POPCNT` counts the set bits in one instruction.
- `BSF` (Bit Scan Forward) finds the position of the lowest set bit — used to locate the first matching byte.

For CSV work, "scan for delimiter" reduces to: broadcast the delimiter byte into a YMM register, then loop comparing 32 bytes per iteration.

## Delimiter scanning

`core/scan.asm` implements the two core scan primitives used by every subcommand:

- **`scan_count_byte(buf, len, byte)`** — counts how many times `byte` appears in `[buf, buf+len)`. Used by `count` to tally newlines.
- **`scan_find_byte(buf, len, byte)`** — returns the offset of the first occurrence of `byte`. Used by `head`, `headers`, field parsing, and search.

### The AVX2 hot loop

The unrolled AVX2 loop in `scan_count_byte` processes **128 bytes per iteration** (four 32-byte `VPCMPEQB` + `POPCNT` sequences):

```nasm
vpbroadcastb ymm0, xmm0       ; broadcast target byte to all 32 lanes

vpcmpeqb ymm1, ymm0, [rdi]   ; compare 32 bytes
vpmovmskb eax, ymm1           ; extract match mask
popcnt eax, eax               ; count matches
add r15d, eax                 ; accumulate

vpcmpeqb ymm1, ymm0, [rdi + 32]
vpmovmskb eax, ymm1
popcnt eax, eax
add r15d, eax
; ... repeated for offsets +64 and +96
```

For `scan_find_byte`, the loop tests the mask with `TEST` and branches on the first hit, using `BSF` to compute the exact byte offset within the 32-byte chunk:

```nasm
vpcmpeqb ymm1, ymm0, [rdi]
vpmovmskb eax, ymm1
test eax, eax
jnz .find_avx2_hit            ; early exit on first match

; on hit:
bsf eax, eax                  ; position of first matching bit
add rbx, rax                  ; add to running offset
```

On DDR4-3200, this saturates memory bandwidth at approximately **30 GB/s** — the theoretical ceiling for sequential reads.

## CPUID detection

Feature detection runs once at startup via `oxsv_init()` → `detect_init` (`core/detect.asm`). The results are cached in three global bytes:

```nasm
; CPUID(1).ECX bit 23 → POPCNT
mov eax, 1
xor ecx, ecx
cpuid
test ecx, (1 << 23)
setnz al
mov [rel detect_has_popcnt], al

; CPUID(7,0).EBX bit 5 → AVX2
mov eax, 7
xor ecx, ecx
cpuid
test ebx, (1 << 5)
setnz al
mov [rel detect_has_avx2], al
```

At runtime, `scan_count_byte` and `scan_find_byte` check `detect_has_avx2` and branch to the AVX2 path or fall back to the SSE2 path (16-byte vectors). The SSE2 path uses `PCMPEQB` + `PMOVMSKB` with the same structure.

<Warning>
  oxsv requires AVX2 at compile time. The runtime check selects between AVX2
  and SSE2 code paths, but the binary is assembled with AVX2 instructions.
  Running on a CPU that predates AVX2 will raise an illegal instruction fault.
</Warning>

## UTF-8 safety

oxsv assumes UTF-8 input. SIMD scanning is safe for UTF-8 because the three ASCII bytes oxsv scans for — `,` (0x2C), `\n` (0x0A), and `"` (0x22) — **never appear as continuation bytes inside UTF-8 multibyte sequences**.

UTF-8 multibyte continuation bytes are always in the range 0x80–0xBF. ASCII bytes (0x00–0x7F) only appear as themselves. This means scanning for any ASCII byte in a UTF-8 stream cannot produce false positives, regardless of what Unicode characters appear in the data.

Japanese text, emoji, and other non-ASCII content pass through unmodified.

<Note>
  Shift_JIS is **not** supported. Shift_JIS byte sequences can include 0x22,
  0x2C, and 0x0A as the second byte of a two-byte character, which would cause
  false delimiter matches. Convert to UTF-8 first:

  ```bash
  iconv -f SHIFT_JIS -t UTF-8 input.csv > input_utf8.csv
  ```
</Note>

## Measured throughput

From `BENCHMARKS.md`, using a 16 MB buffer, `gcc -O2` for the C baseline:

| Function                   | ASM       | C         | Speedup |
|:---------------------------|:----------|:----------|:--------|
| `scan_count_byte` (16 MB)  | 8.9 GB/s  | 3.3 GB/s  | 2.7x    |
| `scan_find_byte` (16 MB)   | 11.3 GB/s | 2.3 GB/s  | 5.0x    |
| `scan_find_byte` (early exit, target at offset ~200) | 8 ns | 88 ns | 10.8x |
| `parse_get_field` (160 B)  | ~20 ns    | ~50 ns    | ~2.5x   |

The early-exit test places the target byte at offset ~200, which is a typical CSV line length. This measures short-scan latency rather than throughput and shows the largest relative gain: 10.8x over the scalar C equivalent.
